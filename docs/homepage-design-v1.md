# 首页设计稿 v2（逻辑版）

日期：2026-10-25 · 状态：待评审
修正：v1 用植物隐喻组织内容，是包装不是拆解。v2 全部改用功能语言：输入什么、用户做什么、数据怎么变、按什么规则判断。

---

## 1. 一条想法在系统里的真实链路

当前代码实际发生的事，按顺序：

| 步骤 | 触发者 | 输入 | 系统动作 | 数据变化 | 产出 |
|---|---|---|---|---|---|
| ① 录入 | 用户 | 任意文本（≤5000 字），可带截图 | 写入 `ideas` 表 | 新增一行：`raw_text`、`status=seed`、时间戳 | 一条未结构化的想法 |
| ② 结构化 | 用户 | 原文 | 填写九字段表单 | 新增 `idea_versions` 一行，`v_no=1`、`origin=manual` | 一份可比较的档案 |
| ③ 验证 | 用户 | 档案里的 `first_step` | **当前无系统动作**：第一步只是文本，没有执行记录 | 无 | 无（这是缺口） |
| ④ 决策 | 用户 | 验证结果（当前也靠记忆） | 手动切换状态 | `ideas.status` 变化 | 状态变更 |
| ⑤ 关联 | 用户 | 两条想法 | 图谱拖拽连线 / 相似度自动边 | `idea_links` 新增一行 | 关系记录 |

**结论**：当前系统只实现了 ① ② ④ ⑤。③ 验证环节没有数据结构，所以「孵化」目前只到"写清楚"，没到"做一次、有结果"。

## 2. 状态机：谁能把状态推到下一步

当前实现里状态可以直接点，没有任何前置校验。合理的规则应该是：

| 当前状态 | 允许动作 | 前置条件（应校验） | 目标状态 | 需要落的数据 |
|---|---|---|---|---|
| seed | 结构化 | 九字段中 4 个必填项完整 | shaping | 版本 v1 |
| shaping | 记录一次验证 | 至少填写：执行日期、动作、结果、证据链接/截图 | proving | 验证记录 |
| proving | 通过 | 结果满足预设判据（在档案里写明） | shipped | 决策记录 + 结论 |
| proving | 不通过 | 填写原因 | paused 或 shaping | 决策记录 |
| shaping / proving | 搁置 | 填写搁置理由 | paused | 理由 + 时间 |
| paused | 恢复 | 说明恢复条件已满足 | shaping / proving | 状态变更记录 |
| 任意 | 合并 | 与另一条想法确认为重复 | 被合并方归档 | 合并关系 |

**现在缺的三样**：
1. 验证记录（日期/动作/结果/证据）
2. 决策记录（结论/理由/时间）
3. 状态流转的前置校验

没有这三样，首页就不能宣称"验证/决策"已完成，只能展示"当前状态"。

## 3. 判断规则（可执行，不是口号）

这些规则决定首页显示什么、提示什么：

| 规则 | 触发条件 | 系统应该显示 |
|---|---|---|
| 值得继续投入 | `problem` 里有具体使用者 + `first_step` 预计 ≤2 晚 + 与已有想法关系明确 | 正常显示，排在前面 |
| 需要合并 | 与另一条想法 Jaccard ≥0.15，且人工确认重复 | 提示「可能是同一件事」 |
| 该搁置 | 在 shaping/proving 停留 >14 天且无新版本 | 提示「该做决定了」 |
| 可以落地 | 验证记录 ≥1 且结果满足预设判据 | 提示「可以标记完成」 |
| 信息不足 | 九字段必填项缺失 | 提示「档案还没写完」 |

首页的"待处理"排序应该按这些规则计算，而不是按创建时间。

## 4. 首页该讲什么（基于真实链路）

首页不是按钮集合，它要回答三个问题，每个问题对应一个区块：

### 区块 A：这个产品到底做什么

一句话（不用比喻）：

> 把一句模糊的话，整理成一份能判断的档案，再用一次最小验证决定继续还是停止。

右侧不再放植物插画，改放**当前数据的流水线**：

```
收件 3  →  已结构化 0  →  验证中 0  →  已决策 0
```

每个数字是真实计数，点击跳到对应筛选。

### 区块 B：一条想法会经历什么

横向五步，每步写清「用户动作 / 数据变化 / 系统规则」：

1. **录入**：写原文 → `ideas` 新增一行
2. **结构化**：填九字段 → `idea_versions` 新增 v1
3. **验证**：按 `first_step` 做一次 → 应新增验证记录（当前缺）
4. **决策**：通过 / 搁置 / 合并 → 状态变更 + 记录理由
5. **关联**：与旧想法连线 → `idea_links` 新增

每步下方用灰色小字标「当前是否已实现」，缺的那步明确标出「待补」，不假装完成。

### 区块 C：现在该处理哪一条

不是"苗圃概览"，是**规则驱动的待办**：

- 需要结构化：seed 且创建 >1 天
- 需要决定：shaping/proving 停留 >14 天
- 可能重复：相似度 ≥0.15 且未连线
- 可以落地：已有验证记录且满足判据（该功能上线后）

每条给一个直接动作链接（去结构化 / 去决策 / 去看重复）。

### 区块 D：输入 + 列表

- 单一输入框（已实现）
- 列表默认按区块 C 的规则排序
- 每张卡显示：状态、停留天数、版本数、下一步动作

## 5. 文案（无隐喻）

**首屏主张**
> 把一句模糊的话，整理成一份能判断的档案，再用一次最小验证决定继续还是停止。

**五步链路标题**
> 一条想法会经历什么

**规则区标题**
> 什么情况下继续投入，什么情况下停

**待办区标题**
> 现在该处理哪一条

**输入区**
> 一个词、一句话、一段对话——想记什么就写什么。

## 6. 视觉

- **去掉植物插画**。首屏右侧改为流水线数字（收件 → 结构化 → 验证 → 决策），用真实数据。
- 颜色只表达状态，不做装饰：seed 琥珀、shaping 蓝、proving 青、shipped 紫、paused 灰。
- 字号层级沿用：page-title 2.05rem / section-title 1.28rem / body 0.95rem / meta 0.75rem。
- 动效只用于页面切换与区块入场，卡片不做逐张浮动。

## 7. 落地需要补的数据结构（不是首页，但首页依赖它）

要让「验证 → 决策」这条逻辑真实成立，需要：

```sql
-- 验证记录
idea_checks (
  id, idea_id, acted_at, action, result, evidence, created_at
)

-- 决策记录
idea_decisions (
  id, idea_id, decision('ship'|'pause'|'merge'|'continue'), reason, decided_at
)
```

首页的"可以落地 / 该搁置"提示依赖这两张表。没有它们，首页只能显示"停了多少天"，不能显示"验证过没有"。

---

## 8. 验收标准

1. 看完首屏能说出：输入什么、系统做什么、最后产出什么
2. 五步链路里每一步都能对应到真实表/字段，缺的那步明确标注
3. 「现在该处理哪一条」不依赖用户自己回忆
4. 不放任何比喻性标题（苗圃/种子/播种/试种）
5. 所有数字来自数据库，不是装饰
